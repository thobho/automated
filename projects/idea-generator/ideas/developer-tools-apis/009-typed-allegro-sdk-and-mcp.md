# 009 — Typed Allegro SDK + MCP server with hosted compliant app (swap-in for rejected I061)
**One-liner:** A maintained TypeScript/Python client for the Allegro REST API plus an MCP server, with a paid hosted layer that registers one compliant Allegro app, handles OAuth for each seller, rate limits (including the mandatory app-specific User-Agent), retries and change alerts. Merges I071 (Allegro API change digest) as a feature. **Written up honestly as the weakest idea of the batch: see the scores and the recommendation at the end.**
**Field:** developer-tools-apis | **Type:** library (with a hosted add-on)
**Target customer:** Polish agencies and in-house developers who build tooling around a client's Allegro sales (offer management, order sync, ads, billing). Count: unknown (unverified). Allegro's developer tracker (github.com/allegro/allegro-api) had 2,543 issues created since 2025-06-01 (GitHub search API, 2026-10-29), which shows a large active developer base but not a count of buyers.
**Problem:** The API has an OpenAPI spec and a sandbox but no official SDK that I could find (the about page lists none): 9,000 requests per minute per Client ID, some per-user leaky-bucket limits, mandatory app registration, and a User-Agent matching the app name with an info URL. New REST API terms from 23 Sep 2025 forbid sharing keys and importing offers to rival marketplaces, and sellers have posted compliance questions (L6-F10, L9-F17).
**MVP scope (≤6 weeks):** (1) Typed client generated from Allegro's swagger.yaml and hand-polished (pagination, error types, rate-limit backoff), TypeScript and Python. (2) OAuth helper (device code and authorization code with PKCE), token store. (3) MCP server on top (read-first, write gate). (4) Hosted layer: one registered app, per-seller OAuth, request proxy with rate-limit budgeting and webhook-like polling for order changes. (5) Weekly change digest from Allegro developer news. (6) Stripe for the hosted tier.
**Why now:** MCP and coding agents create new demand for typed API access (technology shift, L5 3, not a dated rule). Allegro keeps changing terms and withdrawing endpoints (multipack discounts end 12 Jan 2027, turnover-discount resources removed 2 Nov 2026, per L9-F17), which is a reason for a maintained client.
**Foreign analogues:** EmailEngine (Estonia): self-hosted email API, 1,450 USD/year licence, 237 active subscriptions, 19.4k USD MRR, Stripe-verified (TrustMRR): the same "paid developer component for a platform API" model, not the same domain. No direct analogue for an Allegro client (single-marketplace SDKs are free by default). Unverified.
**Competition (PL / global):** Free and open source: chawel/python-allegro (27 stars, last push 2023-12-07), AshmaDev/node-allegro-client (4 stars, 2022-10-29), hopesf/allegro-api-library (1 star, pushed 2026-09-04), wtx-labs Java client (2 stars) (L2-F07, GitHub API); piotrlinski/allegro-open-mcp-server (MIT, Python, 268 MCP tools over about 30 resource groups, OAuth flows, sandbox/production, write gate, 250+ tests, 9 stars, v0.1.0, pushed 2026-05-05, early-stage per the README) already covers the MCP idea; Bilski311/allegro-mcp (1 star). Hosted integrators such as BaseLinker offer their own API with Allegro order sources, limit 100 requests per minute (its docs), and the cross-marketplace tools are where most sellers go (L2-F01..F03). Because Allegro publishes an OpenAPI spec, anyone can generate a typed client with standard generators in minutes (my inference), which weakens the SDK as a paid product.
**Evidence of pain:** Allegro tracker threads: "Pytanie o zgodność z nowym regulaminem REST API" (44 comments), "Regulamin API" (47), Maxapp compliance (58), "Losowe blokady captcha podczas komunikacji z API produkcyjnym" (41), User-Agent notice (47) (L6-F10). These are about terms and blocks, not about missing SDKs; no developer complaint about SDK quality found. The old python-allegro and node client repos show little activity, which is weak evidence of low demand. Search trend: unverified.
**Monetization:** Free SDK; hosted layer 99–299 PLN/month per agency (estimate, unanchored: no competitor price for an Allegro proxy found). Payer: agency or in-house dev team.
**Revenue sketch (estimate):** Assumes 149 PLN/month. 6 months: 6 agencies = about 900 PLN MRR. 12 months: 20 agencies = about 3,000 PLN MRR. 10,000 PLN MRR needs about 67 paying agencies, more than the visible open-source user base suggests (the best Allegro client has 27 stars).
**First 10 customers:** Answer threads in allegro/allegro-api issues with code, publish to npm and PyPI, SEO "Allegro API TypeScript", outreach to agencies that list Allegro integration on their sites.
**Build complexity:** low–medium (generated client, existing MCP examples). Risks: Allegro terms (own key per integrator, sellers connect by OAuth), captcha/blocks on production, a terms change could ban the hosted-proxy pattern.
**Pros / Cons / Risks:** Pros: very cheap to build, testable against the sandbox, agent-friendly. Cons: free OSS MCP already exists, SDK is a spec-generation exercise, payer unclear, platform risk (Allegro can change terms at will, L9-F17). Risks: ban or deprecation, tiny audience.
**Scores (1–5):** L1 1, L2 1, L3 2, L4 3, L5 3, L6 2, L7 3, L8 2, L9 2 | **Weighted:** 2.1 / 5 | **Chance band:** <5% (T16 review: L2 2→1, see Review changes; write-up value was 2.2; shortlist 2.7)
**Cheapest validation test (≤1 week, ≤200 PLN):** Publish the generated TypeScript client and a README to npm for free and post in the Allegro tracker plus two developer communities; success: 30 npm downloads/week and 5 messages asking for hosted features within 2 weeks. If nothing, stop. Cost: nil.
**Kill criteria:** Fewer than 3 inquiries from agencies in 3 weeks; or Allegro publishes an official SDK/MCP; or no agency will pay 99 PLN/month for the hosted layer.
**Confidence:** low
**Recommendation for T16:** consider rejecting this idea and replacing it from the shortlist (next candidates by rank among free field slots: I068 KSeF send queue, which overlaps 003, then others).
**Devil's advocate:** The write-up already recommends rejection, and a second search makes it clear-cut. The GitHub search API (q=allegro+mcp, 2026-10-29, [api.github.com](https://api.github.com/search/repositories?q=allegro+mcp&sort=updated)) returns 18 repositories, of which at least nine are Allegro-marketplace MCP servers pushed between June and October 2026 besides the one already cited: e.g. Zziembie/allegro-mcp-server (offers, orders, billing; pushed 2026-10-11), stepek/allegro-mcp ("tools generated at runtime from the official OpenAPI" spec, 2026-09-10), anetesa/sellerflow-mcp (Allegro order fulfilment, 2026-10-21), wropol/AllegroMCP and ruslan-zhukouski/AllegroMCP ("Unofficial Allegro MCP Server"); all have 0 stars. When every developer with a coding agent can generate the same server from the public spec in an afternoon, the library has a price of zero and no one has shown demand for a paid version (no star above 9 across all of them). The hosted proxy, the only paid part, sits on the wrong side of Allegro's REST API terms risk (one registered app proxying many integrators), and Allegro can change terms or block patterns at will (L9-F17). There is no named payer and no price anchor.
**Review changes:** L2 2→1 (nine-plus free Allegro MCP servers published in 2026, at least one generated from the official spec), weighted 2.2→2.1, band <5% unchanged. Rejected, as T13 recommended. No swap-in from the shortlist in T16: the next free developer-tools candidate I068 (KSeF send queue, 2.7) overlaps 003 and was itself scored as an on-call product (L7 2); T17 can decide whether a replacement is worth writing.
