# API access, approvals and store review: what stands between the founder and a first customer

Lens 7 findings on platform dependencies. All sources accessed 2026-10-29. Each finding names the **gate** (what must be granted by a third party), its **cost or delay**, and a **feasibility reading for this founder** (solo, agentic stack, 6-week MVP, no certification). Readings are my judgement unless a source is cited. IDs `L7-Fnn` are stable anchors.

### L7-F01 — Allegro REST API: every application is reviewed, refusal needs no reason, key must be used within 30 days
- **Evidence:** Allegro's API terms (Regulamin Allegro REST API): access is requested through a form; "Odpowiedź Spółki w sprawie rozpatrzenia wniosku nie wymaga uzasadnienia" (art. 3.4); one key per account; key must be used within 30 days of assignment and at least once every 12 months, the app at least once every 90 days; some features may need a partner programme or "at least 100 app users" (art. 3.2); sharing keys with third parties is banned with a contractual penalty of 50,000 PLN per case (art. 3.11); showing Allegro offers on competing services is banned (art. 4.1c); showing sales statistics about specific users needs a separate agreement (art. 4.1b); changes need 15 days' notice (art. 6.1). A sandbox with a separate app console exists. https://developer.allegro.pl/rules/ and https://developer.allegro.pl/documentation (accessed 2026-10-29; read via a summarising fetch tool, article numbers as reported, not independently re-checked against the PDF).
- **Reading:** the API is self-service to *request* but discretionary to *grant*, and Allegro can change terms at will (see [L6-F10](../06-pain-evidence/ecommerce-and-local-services-pl.md#l6-f10--allegro-tightened-rest-api-terms-on-23-sep-2025-third-party-tool-users-and-developers-filled-github-with-compliance-questions)). The founder can build against the sandbox in week 1, but the production key is a schedule risk and a permanent platform risk. Per-seller OAuth (the seller authorises the app) is the normal model, which avoids partner certification for ordinary seller tools; the "100 users" clause applies to some features only (which ones: unverified).
- **Feasibility mark:** one risky dependency (score 3 on L7 at best); platform can cut the product off (also L9).
- **Confidence:** medium (secondary summary of the terms page).

### L7-F02 — KSeF 2.0 API: public, no integrator certification or approval, free test and demo environments; the cost is protocol complexity and rate limits
- **Evidence:** the Ministry of Finance's integrator guide (dated 05.05.2026, MIT licence) lists authentication, sessions, permissions, offline modes, QR codes, batch/interactive sessions and incremental retrieval, with C# and Java examples from official open-source clients, and mentions no certification or approval step: https://github.com/CIRFMF/ksef-docs . Environments (doc dated 16.03.2026): TEST (release candidates, self-signed certificates allowed, data shared between integrators, "use random NIPs"), DEMO (production-like), PROD (full legal force, "gwarantowanym SLA"): https://raw.githubusercontent.com/CIRFMF/ksef-docs/main/srodowiska.md . Authentication is by XAdES-signed request (certificate) or a KSeF token; generating a token itself needs a one-off XAdES authentication ( https://raw.githubusercontent.com/CIRFMF/ksef-docs/main/tokeny-ksef.md , doc dated 29.06.2025 ). Official clients: ksef-client-csharp (115 stars, last push 2026-10-14) https://github.com/CIRFMF/ksef-client-csharp and ksef-client-java (49 stars, last push 2026-09-25) https://github.com/CIRFMF/ksef-client-java (GitHub API, accessed 2026-10-29).
- **Reading:** best-in-class access for a solo developer: official OpenAPI spec, free environments, no partner programme. Two real costs: (a) qualified-signature or KSeF-certificate handling means the product holds secrets for clients (security duty), (b) rate limits, next finding. Python and Node have no official client (the guide covers C# and Java only); Java is on the founder's stack. A secondary source (poradnikprzedsiebiorcy.pl, not checked against the Ministry) says tokens are valid only until 31 Dec 2026 and certificates become the only method from 1 Jan 2027: **unverified**; it would force certificate handling on any KSeF-authenticated product.
- **Confidence:** high for access model, medium for the token sunset.

### L7-F03 — KSeF rate limits are small and keyed by (taxpayer context, IP); bulk sync must use package export
- **Evidence:** limits doc dated 14.09.2026: limits apply per pair "kontekst + adres IP", sliding windows; exceeding gives HTTP 429 and a dynamic block (`Retry-After`). Examples from the table: invoice metadata query and package export 8 req/s, 16 req/min, **20 req/h**; fetch invoice by KSeF number 64 req/h; interactive send invoice 180 req/h; open session 120 req/h. The doc lists as "niezalecane" syncing only through single-invoice fetches and serving end-user requests by calling KSeF directly instead of a local database: https://raw.githubusercontent.com/CIRFMF/ksef-docs/main/limity/limity-api.md (accessed 2026-10-29).
- **Reading:** an accounting-office product with many clients must keep a local mirror, use `/invoices/exports`, and run polling from stable IPs per client context. This is a design constraint a coding agent can follow if the spec says so, but it is also the likely source of the "KSeF sync" complaints in [L6-F06](../06-pain-evidence/ksef-and-accounting-pain-pl.md#l6-f06--github-cirfmfksef-api-824-issues-120-open-integrators-fight-over-tokens-duplicates-and-change-sync). Hard to test automatically at production scale (limits only visible on PROD/DEMO).
- **Confidence:** high (primary).

### L7-F04 — Peppol: running an Access Point costs EUR 1,050–1,800 sign-up plus EUR 1,850–2,750 a year for a micro company, plus one-off certification of EUR 1,500–2,500; the cheap route is to use an existing AP
- **Evidence:** OpenPeppol fee table for Service Providers joining from 1 July 2025: Access Point only, 1–50 employees: sign-up EUR 1,050, annual EUR 1,850; Access Point + SMP, 1–10 employees: EUR 1,800 sign-up, EUR 2,750 annual; certification one-off EUR 1,500 (AP only) or 2,500 (AP + SMP): https://peppol.org/join/fees/ . A secondary 2026 guide (avask.com, vendor blog, low reliability) adds that a self-run AP also needs a Service Provider Agreement with the national Peppol Authority, ISO 27001 and AS4 infrastructure: https://avask.com/blog/how-to-get-a-peppol-id/ . HN thread: a SaaS owner says an own AP costs "a basic yearly fee of 2000 euros" ([L6-F15](../06-pain-evidence/dev-and-api-pain.md#l6-f15--ask-hn-how-are-you-preparing-for-peppol--67-points-76-comments-cost-of-an-access-point-and-my-bookkeeping-software-will-handle-it-both-appear)).
- **Reading:** about EUR 3,000 in year one plus audits is above the 500 PLN/month budget (roughly 2,150 PLN a year only at EUR 1,850 — conversion rate not sourced; treat as estimate), and the ISO 27001 claim is unverified. Products that only *generate or read* XRechnung/ZUGFeRD/FA(3) files need no AP. Products that *transmit* over Peppol should resell an existing AP's API (pricing not checked here).
- **Confidence:** high for fees, low for the ISO claim.

### L7-F05 — Shopify App Store: public apps need a review with a screencast, test credentials, Lighthouse impact ≤10 points and Shopify billing; revenue share is 0% on the first USD 1,000,000
- **Evidence:** app requirements checklist: privacy policy required, 1200×1200 icon, 3–6 screenshots at 1600×900, OAuth first, charge through Shopify App Pricing, plans changeable without support contact, "shouldn't reduce Lighthouse performance scores by more than 10 points", third-party integrations need valid test credentials: https://shopify.dev/docs/apps/launch/app-requirements-checklist . Revenue share: developers keep 100% of the first USD 1,000,000 lifetime gross app revenue (only revenue from 1 Jan 2025 counts), 85% above; one-time USD 19 registration; separately a 2.9% processing fee: https://shopify.dev/docs/apps/launch/distribution/revenue-share (both accessed 2026-10-29). Review turnaround time is **not** stated on these pages: unverified.
- **Reading:** self-serve, well documented, testable (Shopify CLI dev stores are free; free dev-store claim is from my knowledge, not sourced here). Zero platform fee at the founder's scale is a strong economics point. The risk is a rejection loop on UI/performance rules; embedded admin UI uses Polaris (design system, so no pixel-perfect design needed).
- **Confidence:** high for rules, none for timeline.

### L7-F06 — Google Play: new personal developer accounts must run a closed test with at least 12 testers for 14 consecutive days before production
- **Evidence:** Play Console Help: for personal accounts created after 13 Nov 2023, "a minimum of 12 testers who have been opted in continuously for at least 14 days"; a tester who opts out and rejoins restarts the 14 days: https://support.google.com/googleplay/android-developer/answer/14151465 (accessed 2026-10-29). A device-verification article for new accounts exists and was not read.
- **Reading:** adds at least two weeks and a recruiting task (12 real people) to any Android-first product, which eats the 40 h/month non-code budget in the launch month. Together with native-polish risk it argues for web apps/PWAs over store apps (the BRIEF already marks native polish down). An organisation account (needs a D-U-N-S number: from my memory, unverified) may avoid the rule; not checked.
- **Confidence:** high.

### L7-F07 — Chrome Web Store review takes "a few days" up to "a few weeks"; new developers, broad host permissions and obfuscated or large code lengthen it
- **Evidence:** https://developer.chrome.com/docs/webstore/review-process : "For most extensions, review is completed within a few days, but it can take up to a few weeks"; contact support after three weeks; extended review for new developers or new extensions, dangerous permissions, broad host permissions, large or hard-to-review code, prior rejections (accessed 2026-10-29). Registration fee is not on that page (unverified here).
- **Reading:** an extension that touches only one host (an Allegro seller panel, a KSeF page) with narrow permissions is a 1–3 week release path, and the review is predictable. A first-time publisher should assume the long end.
- **Confidence:** high.

### L7-F08 — WordPress.org plugin directory: initial review about four weeks, stated target "within fourteen days" for small correct plugins; more than 3,500 plugins are mid-review at any time
- **Evidence:** https://developer.wordpress.org/plugins/wordpress-org/plugin-developer-faq/ (accessed 2026-10-29): zip under 10 MB, production-ready, one plugin in review at a time, review open up to three months, plugins that copy core functionality or "frameworks/libraries" not accepted, "phoning home" and unnecessary external calls flagged.
- **Reading:** a SaaS-connector plugin (WooCommerce–KSeF bridge, [L2](../02-weak-competition/README.md)) fits, but a plugin that mostly calls the author's own API for core function may be questioned (guideline detail not read: unverified). A paid add-on can also be sold from the founder's own site and skip the directory, at the cost of discovery (lens 8).
- **Confidence:** medium.
