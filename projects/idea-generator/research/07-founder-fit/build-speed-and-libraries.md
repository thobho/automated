# Build speed: open-source building blocks and what is known about AI-assisted delivery time

Lens 7 findings on how long an MVP takes and what shortens it. GitHub figures come from the public GitHub API (stars, licence field and last-push date as returned on 2026-10-29). IDs `L7-Fnn` are stable anchors. Delivery-time evidence for AI-built products is weak everywhere; this file says so.

### L7-F21 — E-invoicing is the best-supplied area for open-source building blocks (Java, Apache-2.0, pushed this week)
- **Evidence (GitHub API, accessed 2026-10-29):** ZUGFeRD/mustangproject (ZUGFeRD/Factur-X/XRechnung library, 488 stars, Apache-2.0, last push 2026-10-28) https://github.com/ZUGFeRD/mustangproject ; itplr-kosit/validator (the German KoSIT XML validator, 192 stars, Apache-2.0, push 2026-10-26) https://github.com/itplr-kosit/validator ; phax/phive (Peppol/XRechnung validation engine, 77 stars, Apache-2.0, push 2026-10-28) https://github.com/phax/phive ; phax/phoss-smp (Peppol SMP server, 212 stars, licence field "NOASSERTION", push 2026-10-29) https://github.com/phax/phoss-smp ; ConnectingEurope/eInvoicing-EN16931 (the EU validation artefacts, 268 stars, push 2026-10-26) https://github.com/ConnectingEurope/eInvoicing-EN16931 .
- **Reading:** a German E-Rechnung reader/generator/validator is mostly glue around maintained Java libraries on the founder's stack, which an agent can wire up in days, and tests are automatable (sample files, validators). The flip side is crowding ([L6-F16](../06-pain-evidence/dev-and-api-pain.md#l6-f16--counter-evidence-at-least-8-show-hn-e-invoice-tools-in-2026-each-got-13-points)): low build cost means low entry barrier for rivals.
- **Confidence:** high on facts.

### L7-F22 — KSeF: official C# and Java clients plus a long tail of community clients in Python and TypeScript, all MIT
- **Evidence (GitHub API search "ksef" by language, 2026-10-29):** Python 154 repos (top: stacking-hq/ksef2 82 stars, MIT, push 2026-10-28; smekcio/ksef-client-python 29 stars, MIT, push 2026-10-28); TypeScript 94 repos (CIRFMF/ksef-pdf-generator 81 stars, MIT; Flopsstuff/ksef-client-ts 18 stars); Java 27 repos (CIRFMF/ksef-client-java 49 stars, MIT, push 2026-09-25; alapierre/ksef-java-rest-client 46 stars, Apache-2.0, last push 2025-10-01, i.e. likely stale vs KSeF 2.0). Official: CIRFMF/ksef-client-csharp 115 stars. Links: https://github.com/stacking-hq/ksef2 , https://github.com/smekcio/ksef-client-python , https://github.com/CIRFMF/ksef-client-java , https://github.com/alapierre/ksef-java-rest-client .
- **Reading:** the founder does not start from zero for any KSeF product, in Java via the official client; Python/Node via young community clients (quality unverified, not code-reviewed). A "KSeF client" library is not a moat. The count also supports the L2 crowding conclusion.
- **Confidence:** high on counts; low on library quality.

### L7-F23 — Open-source application bases exist for booking and invoicing, but copyleft and unclear licences constrain a commercial fork
- **Evidence (GitHub API, 2026-10-29):** alextselegidis/easyappointments (PHP booking app, 4,464 stars, **GPL-3.0**, push 2026-10-26) https://github.com/alextselegidis/easyappointments ; invoiceninja/invoiceninja (PHP, 10,366 stars, licence field "NOASSERTION", push 2026-10-29) https://github.com/invoiceninja/invoiceninja ; InvoicePlane/InvoicePlane (PHP, 3,265 stars, "NOASSERTION") https://github.com/InvoicePlane/InvoicePlane ; odoo/odoo (Python, 55,403 stars, "NOASSERTION") https://github.com/odoo/odoo . The "NOASSERTION" value means GitHub could not classify the licence; the actual terms (e.g. source-available restrictions) were **not read**. Cal.com's repository lookup returned a redirect and was not checked.
- **Reading:** GPL-3.0 does not forbid selling hosted SaaS, but a modified fork served over a network has different obligations depending on the licence (AGPL vs GPL; not analysed here). The founder's stack is Java/Node/Python/React, so PHP bases mean extra context for agents. Greenfield builds with an agent are the more likely path for 6-week MVPs; bases are useful as *reference specifications* for tests.
- **Confidence:** medium.

### L7-F24 — METR: the best controlled evidence on AI coding speed-up is weak and has moved from "19% slower" (early 2025) to "unreliable, probably faster" (late 2025)
- **Evidence:** METR, 24 Feb 2026: early-2025 randomized study found tasks took 19% longer with AI (95% CI +2% to +39%); late-2025 follow-up estimated -18% task time for returning developers (n=10, CI -38% to +9%) and -4% for new developers (n=47, CI -15% to +9%), both CIs include zero; METR calls the data "an unreliable signal of the current productivity effect of AI tools" because many developers refused to work without AI (selection bias towards less speedup), tasks were withheld, pay was cut from USD 150/h to 50/h; METR believes speed-ups are likely larger in early 2026 but the data is "only very weak evidence" for it: https://metr.org/blog/2026-02-24-uplift-update/ (accessed 2026-10-29). The sign convention was reported confusingly by secondary sources; the figures above are METR's own, via a summarising fetch.
- **Reading:** no rigorous number supports "an agentic stack makes the founder 5× faster". Plan with review time as the bottleneck (BRIEF: founder reviews). Applies to the 6-week bar of L7: score MVP scope conservatively, favour specifiable, testable work.
- **Confidence:** high (primary), but about the limits of the evidence.

### L7-F25 — Public "idea to production" timelines for Claude-Code-built SaaS are self-reported and promotional: two named cases, 4 hours (prototype) and 55 days (multi-tenant SaaS)
- **Evidence:** a vendor blog (Build This Now, which sells a USD 29 starter kit; low reliability) reports: a sponsorship-matching tool in about 4 hours (prototype, reported); OnboardingHub, a multi-tenant SaaS, 55 days, 727 commits, 43 database migrations (as reported by its builder); its own tiers, labelled estimates: prototype 4–72 h, shippable MVP 1–4 weeks (30–80 h), production SaaS 4–8 weeks part-time (80–200 h): https://www.buildthisnow.com/blog/real-examples/idea-to-production-time-data (accessed 2026-10-29). The page cites Stanford "2.74× more security issues in AI-co-authored code" without a source in the text (unverified). A broader search (9 results: DEV Community playbooks, agency blogs) gave no verified solo post-mortem with dates and revenue.
- **Reading:** the honest public record supports "weeks for a narrow MVP, 8 weeks for a multi-tenant SaaS", not "days". The 55-day case is part of a daily-driver SaaS with multi-tenancy and billing, which suggests ≤6 weeks needs single-tenant-simple scope: one user type, one integration, one billing plan. This is an inference.
- **Confidence:** low.
